## Why this matters

qrcc の中心機能（生成と読み取り）は**すべて端末内の wasm で動く**（ADR-0003）。
つまり**オフラインで本当に使える**のに、いまはネットワークが無いと
ページすら開けない。

PWA にすると 2 つ効く。

1. **ホーム画面に追加できる。** Android でも iOS でも。バーコードを扱う道具は
   現場で開くものなので、アプリのように起動できる価値は大きい
2. **Workers のリクエストが減る。** アセットが端末側にキャッシュされるぶん、
   無料枠（100k req/日）の消費が下がる（ADR-0009 と同じ向き）

**この計画ではプラグインを使わない**（オーナーの判断）。`vite.config.ts` は
`cloudflare()` と `tanstackStart()` の順序が公式手順どおりに厳密で、
この 2 つの相性問題は Cloudflare 側に issue も立っている。3 つ目のプラグインを
足すリスクを取らず、**`public/` に静的ファイルを置くだけ**で完結させる。

### PWA にしても iOS で NFC は使えない

念のため。Web NFC は WebKit が実装しておらず、ホーム画面に追加しても変わらない。
これは調査済みの事実で、この計画の目的ではない。

## 第 1 段階: ホーム画面に追加できるようにする

### アイコンの図案（指定）

ブランド素材が無いので、**QR コードの位置検出パターン（隅の四角）** を
モチーフにする。16px でも QR だと分かり、商標の問題も無い。

`services/web/public/icon.svg` を次の要件で作る。

- 512 × 512、背景は角丸の正方形、色は **`#004fa7`**
  （`--qrcc-accent` のライト側 `oklch(0.44 0.16 255)` を sRGB に変換した値）
- 前景は **白**（`#ffffff`）。位置検出パターンを 3 つ（左上・右上・左下）。
  各パターンは「外枠の正方形＋内側の塗り正方形」の入れ子
- 右下には小さな正方形をいくつか散らして、QR らしさを出す
- **マスカブル用は図柄を中央 80% に収める。** Android は円形などに切り抜くので、
  端まで描くと欠ける

### PNG への変換

```bash
bunx sharp-cli --input services/web/public/icon.svg --output services/web/public/icon-512.png resize 512 512
```

**`sharp-cli` をリポジトリの依存に入れないこと。** `bunx` の一回きりで生成し、
**PNG だけをコミットする**。`bun.lock` が変わったら `git checkout -- bun.lock` で戻す。

必要なサイズ: `icon-192.png`(192) / `icon-512.png`(512) /
`icon-maskable-512.png`(512、マスカブル用の SVG から) /
`apple-touch-icon.png`(180)。

**この方法が動くことは計画作成時に検証済み**（512×512 の有効な PNG が出た）。

### manifest

`services/web/public/manifest.webmanifest`:

- `name` / `short_name`（`qrcc`）/ `description` は `documentHead` の文言と揃える
- `start_url: "/"`、`scope: "/"`、`display: "standalone"`
- `background_color` と `theme_color` はライト側の値
- `icons` に上の 3 つ（`purpose` は `any` と `maskable` を分ける）
- `lang: "ja"`、`dir: "ltr"`

### `<head>` への追記

`documentHead` の `links` に:

- `{ rel: 'manifest', href: '/manifest.webmanifest' }`
- `{ rel: 'icon', href: '/icon.svg', type: 'image/svg+xml' }`
- `{ rel: 'apple-touch-icon', href: '/apple-touch-icon.png' }`

`meta` に **`theme-color` を 2 つ**（ライト / ダーク）:

```ts
{ name: 'theme-color', content: '#ffffff', media: '(prefers-color-scheme: light)' }
{ name: 'theme-color', content: '#0f1217', media: '(prefers-color-scheme: dark)' }
```

ダーク側の値は `--qrcc-surface` のダーク（`oklch(0.18 0.012 265)`）を
sRGB に変換したもの。**片方だけ書かないこと。** このアプリは両テーマを
真面目に作っているので、片方だけだとアドレスバーの色が食い違う。

## 第 2 段階: Service Worker（プラグインなし）

`services/web/public/sw.js` に**素の JavaScript** で書く。ビルドを通さないので
TypeScript は使えない。**その代わり `vite.config.ts` に触らずに済む。**

### キャッシュの方針（ここが肝。間違えると事故になる）

| 対象               | 方針                                    | 理由                                                                                             |
| ------------------ | --------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `/assets/*`        | **cache-first**                         | 内容ハッシュ付きのファイル名。中身が変わればファイル名も変わるので、古いものを配る事故が起きない |
| ページ遷移（HTML） | **network-first**、失敗したらキャッシュ | SSR の結果。network-first でないとデプロイが反映されない                                         |
| `/_serverFn/*`     | **キャッシュしない**                    | 保存・一覧・共有。POST もある                                                                    |
| `/api/auth/*`      | **キャッシュしない**                    | 認証                                                                                             |
| それ以外           | 素通し                                  |                                                                                                  |

**GET 以外は一切触らないこと**（`event.request.method !== 'GET'` なら即 return）。

### HTML をキャッシュしてよい URL を限定する

**認証が要るページの HTML をキャッシュしてはならない。** `/codes` は利用者の
保存したコードが載る。共有端末で次の人に見えると事故になる。

キャッシュしてよいのは**公開ページだけ**:

```js
const CACHEABLE_PAGES = ['/', '/print', '/settings', '/sign-in', '/nfc']
```

`/codes`、`/codes/*`、`/shared/*` は **network-first で、成功しても保存しない**
（共有リンクのトークンは秘密）。

### 版管理

- キャッシュ名に版を持たせる（`qrcc-v1` など）
- `activate` で**自分の版以外のキャッシュを全部消す**
- **`skipWaiting()` を呼ばないこと。** 呼ぶと、開いているページの途中で
  アセットの世代が入れ替わり、古い HTML が新しいチャンクを要求して壊れる。
  新しい SW は次にページを開いたときに有効になればよい

### 登録の配線

`features/shell/ui/register-sw.ts`:

```ts
/** Service Worker を登録する。対応していない環境では何もしない。 */
export const registerServiceWorker = (container: ServiceWorkerContainerLike | undefined): void
```

- **`navigator` を直接触らない。** 引数で受け取る（テストで偽物を渡せる）。
  `features/scan/ui/browser-scan.ts` と同じ方針
- 失敗しても**例外を投げない**（登録に失敗してもアプリは動くべき）
- `features/shell/ui/root.route.tsx` の `useEffect` から呼ぶ。
  **ハイドレーション後だけ**（SSR では `navigator` が無い）

**Verify（第 2 段階）**:
`bun test features/shell` → 全 pass。`bun run check` → exit 0。

### e2e（この計画の目玉）

1. `/manifest.webmanifest` が 200 で、`name` / `icons` / `start_url` を含む
2. アイコン 4 つがすべて 200 で、**中身が空でない**
3. `<link rel="manifest">` が HTML に出ている
4. Service Worker が登録され、ページを制御する状態になる
   （`navigator.serviceWorker.controller` が埋まる。**固定待ちを使わず**
   `page.waitForFunction` で待つ）
5. **オフラインにしても生成が動く**
   - オンラインで `/` を開き、プレビューが出るまで待つ（＝ wasm 取得済み）
   - `context.setOffline(true)` にしてリロード
   - **生成のプレビューが出ること**
6. **`/codes` の HTML がキャッシュされないこと**
   - `/codes` を開いたあとオフラインにしてリロードし、
     キャッシュから復元されないこと（利用者のデータが残らない）

**5 が通れば PWA として本物**。ここが落ちるならこの計画の価値は無い。

## Maintenance notes

- **Service Worker は「古い版を配り続ける」事故が一番怖い。** `/assets/*` が
  内容ハッシュ付きであること、HTML が network-first であること、
  `skipWaiting()` を呼ばないこと。この 3 つが崩れたら事故になる
- **`sw.js` は素の JS なので typecheck も lint の型情報も効かない。**
  だからこそロジックを増やさないこと。増やしたくなったらビルドに組み込む
  判断（＝プラグイン導入）を改めてすること
- 公開ページの一覧（`CACHEABLE_PAGES`）は**手で管理している**。
  新しい公開ページを足したらここにも足す。逆に**認証が要るページを
  絶対に足さないこと**
- 一度 SW を配ると利用者の端末に残る。**やめるときは「自分を unregister して
  キャッシュを消す SW」を配る必要がある**。単にファイルを消すだけでは
  古い SW が動き続ける
