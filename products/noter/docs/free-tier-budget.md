# 無料枠の予算と縮退動作

**Workers Free プランに留まる。** 上限に達しても課金されず、エラーになって止まるだけ。
数値は 2026-09-06 に Cloudflare 公式ドキュメントで確認したもの。変更があれば
この表を先に直す。

## 1. 上限（1 日、UTC リセット）

| リソース             | Free 上限   | noter での消費単位                                                   |
| -------------------- | ----------- | -------------------------------------------------------------------- |
| Workers リクエスト   | 100,000     | ページ表示・server function・`/ws/` Upgrade・`/api/auth/*`           |
| Workers CPU          | 10 ms/req   | SSR が主。解析系はブラウザなので余裕                                 |
| DO リクエスト        | 100,000     | WS 接続 1、**WS 受信 20 通 = 1**、alarm 1、内部 fetch 1。送信は無料  |
| DO duration          | 13,000 GB-s | 実行中 or 非 hibernation の待機のみ。hibernation 中は 0              |
| DO SQLite 行書き込み | 100,000     | alarm flush 1（+ setAlarm ~1）、attachment 更新                      |
| DO SQLite 行読み取り | 5,000,000   | wake 時の state 読み込み                                             |
| DO SQLite ストレージ | 5 GB        | 文書 1 本 ≤ 1.5 MB                                                   |
| D1 行書き込み        | 100,000     | 文書作成・rename・共有・メンバー登録・`updated_at` touch・セッション |
| D1 行読み取り        | 5,000,000   | セッション検証・一覧・`/ws/` 認可                                    |
| D1 ストレージ        | 5 GB        | メタデータのみ                                                       |

**R2 / KV は使わない**（ADR-0009）。R2 は無料枠超過を止められない。

## 3. 到達目安（どれが先に枯れるか）

前提: 1 人が**アクティブに編集**する 1 時間 = 入力 3,000 通 + カーソル 3,000 通 =
6,000 通 → **300 DO req/時**。同じ時間、alarm flush = 720 回 → **720 DO req/時、~1,440 rows/時**。

| 枯れる順 | リソース      | 目安                                                                     |
| :------: | ------------- | ------------------------------------------------------------------------ |
|    1     | DO 行書き込み | 100k / 1,440 ≈ **69 文書・時間/日**（同じ文書を何人で編集しても 1 本分） |
|    2     | DO リクエスト | 100k / (300 + 720) ≈ **98 ユーザー・時間/日**                            |
|    3     | Workers       | 100k ≈ ページ表示 + WS 接続。**1 日 3 万回開いても余る**                 |
|    4     | D1 書き込み   | セッション更新（1 日 1 回/人）+ 文書操作。**数千人規模まで無視できる**   |

個人〜小チーム（同時 10 人、1 日合計 30 文書・時間）なら 5 割以下で収まる。
**alarm 間隔（`PERSIST_DELAY_MS`）が最大のレバー**: 5 s → 15 s で行書き込みが 1/3。

## 4. 縮退動作（上限に達したとき）

| 枯れたもの         | 何が起きるか                           | UI の振る舞い                                                                                                                                                                                      |
| ------------------ | -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| DO リクエスト      | 新規 WS 接続と受信メッセージがエラー   | `ConnectionState.rejected('limit')`。「本日の同期上限に達しました。編集はこの端末に保存され、翌日 09:00（JST）以降に同期されます」。Y.Doc はブラウザに残る                                         |
| DO 行書き込み      | alarm flush が失敗                     | DO はメモリで配信を続ける（接続中の全員は同期し続ける）。flush 失敗をログ。全員が離れると最大 5 秒〜最終 flush 以降の差分が失われうる → 「保存できていません」を表示し、**ローカル書き出しを促す** |
| Workers リクエスト | ページが開けない（1027 エラー）        | Cloudflare のエラーページ。開いているエディタは WS が生きていれば動き続ける                                                                                                                        |
| D1 書き込み        | 文書作成・共有・ログインが失敗         | 「本日の作成上限に達しました」。既存文書の編集は影響なし（DO の D1 書き込みは touch だけで、失敗は無視する）                                                                                       |
| DO ストレージ 5GB  | 実質到達しない（~3,000 文書 × 1.5 MB） | 作成時に `MAX_DOCUMENTS_PER_USER` で先に止まる                                                                                                                                                     |

**原則: 枯れても既に開いている人の編集は止めない。ブラウザの Y.Doc が真実で、
サーバは配送と保管の手段。** ローカル書き出し（ダウンロード）は常に使える。

## 5. 監視

- Cloudflare ダッシュボードの Workers / DO / D1 のメトリクス（日次）。
- DO の `console.log` は `observability.enabled = true` で Workers Logs に出る
  （Free: 20 万行/日、3 日保持）。`persist_failed` / `over_limit` だけを出す。
- 50% を超えたら `PERSIST_DELAY_MS` を延ばす。80% を超えたら awareness の
  送信間隔（`features/sync/client/src/batching.ts`）を入れる。
